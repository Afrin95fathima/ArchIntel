## What the tool does

ArchIntel inspects a compiled Java application and produces architecture graphs, candidate domains, technical-debt findings, modernization readiness, and a suggested investigation sequence. The uploaded application is never launched. Results describe static structure (classes, methods, references in bytecode), not production behavior; Dynamic analysis adds OpenTelemetry spans.

Northstar Commerce is a **synthetic demonstration application**. Its results are generated by the same real jQAssistant â†’ Neo4j â†’ architecture-engine pipeline used for uploads.

## Start and stop

On the prepared Windows machine:

1. Open this project folder and double-click **Start-ArchIntel.cmd**.
2. Wait for â€œArchIntel ready.â€
3. The browser opens **http://127.0.0.1:8000**.
4. Complete administrator setup or sign in, then confirm **Services ready** in the top bar. See [Phase 1 user flow](PHASE-1-USER-FLOW.md) for the setup key and access controls.

Open **Local setup** in the left navigation for environment diagnostics. This page checks the configured database, local Java static-analysis runtime, and ArchIntel data folder. It distinguishes optional runtime-agent/local-model setup from container-based candidate build and security workflows, which are deferred in the local POC. Docker is not needed for ordinary static analysis or for receiving runtime telemetry; runtime capture also requires an OpenTelemetry Java agent in the application being observed.

The launcher starts workspace-local PostgreSQL and the API in hidden background processes. The prepared runtime does not require Docker or an external API key. Internet is needed for the initial setup only; the Northstar Commerce demonstration runs offline.

After a reboot, run Start-ArchIntel.cmd again. To stop, wait for analyses to finish and double-click **Stop-ArchIntel.cmd**. Saved results remain in `.data/postgres`; do not delete that folder.

## Upload your own application

1. Select **Applications**, then **Analyze application**.
2. Choose a project or enter a new project name.
3. Enter an application name and version.
4. Choose a compiled `.jar` or `.war`, or a compiled project `.zip` containing one or more module `target/classes` / `build/classes` folders or module JAR/WAR files.
5. Click **Start architecture analysis**.
6. Follow progress until the overview appears.

Supported packaging: ordinary JARs, WAR classes under `WEB-INF/classes/`, Spring Boot classes under `BOOT-INF/classes/`, and compiled multi-module project ZIPs. A source-only ZIP is rejected: ArchIntel does not compile or execute uploaded application code. For Concord on Windows, package its existing build outputs with `powershell -NoProfile -ExecutionPolicy Bypass -File D:\vfunction\scripts\package-java-project-zip.ps1 -SourceRoot E:\concord\concord -OutputZip E:\concord\concord-compiled-classes.zip`. On macOS or Linux use `scripts/package-java-project-zip.sh <source-root> <output.zip>`. Both scripts add every module `pom.xml` (and Gradle build files), which lets ArchIntel resolve dependency versions through parent poms and in-archive BOMs for the Technology lifecycle screen. The ZIP is limited to compiled class files under recognized build-output folders plus those build descriptors, and excludes VCS/dependency caches. A source checkout is registered separately in Source tasks (the ZIP holds classes only).

Project ZIP classes from different modules are combined into one structural graph. Identical duplicates are collapsed. If modules contain different bytecode with the same fully qualified class name, ArchIntel analyzes the first normalized project path and records the selected and skipped paths in the ZIP manifest; the Overview calls out these conflicts. Review them before relying on dependencies involving those classes. Nested dependency JARs are not recursively scanned. References to external libraries (for example org.springframework.*) are stored as external references, not as application classes. Multi-release override classes (META-INF/versions) are skipped; the base classes are analyzed. Classes produced by Immutables, jOOQ and OpenAPI Generator clients are excluded from the graph by default (the Overview shows how many and which generators); set `EXCLUDE_GENERATED_CODE=false` to analyze them as application code.

Default safety limits: 100 MB uploaded, 400 MB expanded, 50,000 entries, 20,000 classes, and 200,000 extracted dependency rows. These 5 limits protect the server; they are **not a measured capacity** for large applications.

The upload is rejected on: path traversal (..), malformed archive, encrypted entry, symbolic link, duplicate normalized class path, or expansion beyond 400 MB. Upload artifacts are removed after successful processing by default. Failed inputs are retained for retry; structured results and the artifact hash are retained.

## Processing progress

The stages are validation, scanning, graph extraction/building, cycle analysis, metrics, domain discovery, issue analysis, modernization, and result persistence. Each stage records duration. A failed run names the failed stage (one of 9) and shows no partial findings.

One job executes at a time. Up to 4 jobs can be queued or running. Refreshing the browser does not cancel the run; the job runs in the API process. On startup, queued/interrupted work restarts from its original artifact when available; missing inputs produce an actionable recovery failure.

## Overview

The overview shows filtered application classes/packages, distinct internal dependency pairs, external references, candidate domains, issues, and average structural readiness. It also identifies the artifact SHA-256, scanner, and algorithm version.

A class pair can have 2 or more dependency types (for example field and call). The typed-edge count can therefore exceed the distinct-pair count: a field plus a call between 2 classes gives 2 typed edges and 1 pair. Average Readiness is not a forecast of migration cost or duration.

## Architecture explorer

- Switch between **Domains**, **Packages**, and **Classes**.
- Click a node for details; double-click a domain/package to expand it.
- Use the domain filter to narrow a large view.
- Drag nodes, pan, scroll to zoom, and use the lower-right fit button.
- Clear the package filter to list every class of the selected domain (up to 150 nodes).

An arrow points **from the dependent class to its dependency**: OwnerController -> OwnerRepository means the controller uses the repository. Views are capped at 150 displayed nodes and 2,000 edges; a notice identifies truncation. An edge is drawn only when both endpoints are among the 150 visible nodes. The class graph and the package graph are separate: the packages owner and visit can form a package cycle while no class cycle exists (Owner uses Visit, Pet uses Owner, with no loop between classes).

## Candidate domains

Cards show names, class/package counts, heuristic confidence, outgoing cross-domain ratio, issues, and readiness. Open a card for grouping evidence, database signals, dependency counts, and class membership.

Confidence = weighted evidence support (see Glossary), not the probability that the boundary is right. Validate boundaries and naming with domain owners. Boundaries are generated by the algorithm; a reviewer can accept, rename or reject them in the Review tab.

## Technical debt and cycles

Filter findings by severity, rule id, domain or package/class text. Expand a finding to inspect its affected entity, evidence, significance, and recommended investigation.

Rules cover circular dependencies, large cyclic clusters, cross-domain coupling, god-class candidates, unstable-package dependencies, main-sequence deviation, high fan-in/out, and boundary violations. A god-class candidate needs 2 or more outlier signals (methods, fan-out, complexity, LCOM), not method count alone.

Cycle cluster membership is complete; the listed cycle paths are samples capped by max_cycles_per_scc. Clusters above max_cycle_length skip path enumeration and keep the member list and internal edge count. A cluster with no listed short cycle still contains cycles, because a strongly connected component with 2 or more members has at least 1.

## Architecture metrics

| Metric | Meaning |
|---|---|
| Ca | Distinct outside classes that depend on a package's classes. |
| Ce | Distinct outside classes depended on by a package's classes. |
| I | Instability: `Ce / (Ca + Ce)`; zero when both are zero. |
| A | Abstract classes or interfaces / all package classes, counted once per type. |
| D | Distance: `abs(A + I - 1)`. |

Read I together with A and the package role: a utility package with I near 0 and A near 0 is stable but concrete. A high I (near 1) or a low I (near 0) is not a defect on its own. Isolated packages are identified separately. The scatter plot diagonal is the main sequence A + I = 1; hover a point for its Ca, Ce, I, A and D.

## Modernization plan

Readiness is a 0â€“100 weighted structural score used to prioritize investigation. A higher Readiness comes from higher cohesion, fewer cross-domain dependencies, no cycle membership and a single owner of each repository. A lower Readiness points to the lowest component: cycle removal, fewer boundary dependencies or a resolved shared repository. Readiness (0-100) does not predict migration cost or duration. Open a row or candidate-domain detail to inspect the assessment's actual components, weights, risks, and formula. The formula stored with each assessment (readiness_formula) overrides this manual for that assessment.

Unknown database evidence is excluded from Readiness (weights renormalised) and is listed under not measured. The displayed range (low-high) comes from shifting each weight by 10 points, not from a statistical interval. Confidence describes the evidence behind a domain boundary and is separate from Readiness. The tool does not infer runtime SQL, transactions, table ownership, or a data migration plan.

The sequence is **dependency first**: a domain in wave 3 depends only on domains in waves 1 and 2. Readiness prioritizes within a wave. Domains in one cyclic group (see Dependencies) need one joint fix; the row order inside the group is not an extraction order.

## Export and manuals

The Application architecture page exports bounded system, module, and package relationship diagrams as Mermaid, SVG, or PNG. Use **Print / PDF** to open the browser print dialog and save the map as PDF. Switch between dependency, modernization-wave, and before/after scan views. Node colour = highest debt severity, runtime coverage or modernization wave; a red outline marks cycle membership. Before/after colors mark added, removed, and unchanged node identities. SVG/PNG export the selected graph; choose the before or after side when comparing scans. Class-level graphs remain capped and are explored separately. **Export analysis** downloads JSON containing graphs, metrics, domains, issues, cycles, readiness components, sequencing, configuration, limitations, and artifact identity. On Applications, select two completed scans of the same app to compare read-only baseline drift. Exact class/domain identities and dependency tuples are compared; scores and finding counts may also change with scanner or algorithm versions. Runtime observation gaps are workload-specific: use Dynamic analysis to inspect observed and unobserved items, where â€œnot observedâ€ does not mean unused.

## Troubleshooting

| Symptom | Action |
|---|---|
| Cannot connect | Run the launcher and use port 8000, not an old development tab. |
| Services unavailable | Inspect `.data/api.err.log` and `.data/postgres.err.log`; retry the launcher after startup. |
| Scanner runtime incomplete | Follow setup/exporter-build instructions in the developer guide. |
| Upload rejected | Confirm a compiled JAR/WAR within the archive limits. |
| No internal classes remain | Have a developer review `EXTERNAL_PREFIXES` for your application's namespace. |
| Queue full | Wait for an existing run to finish. |
| Run interrupted by restart | Restart ArchIntel. Queued/interrupted runs resume automatically when their original artifact is available. If recovery reports a missing artifact, upload it again. |
| Scan failed | Correct the reported cause and start analysis again for the application. The failed input is retained for retry; the previous failed run remains in history. A checksum failure requires uploading the original artifact again. |
| Browser origin is not allowed | Open the tool directly at its localhost URL. A developer must explicitly configure trusted origins and hosts for a different deployment. |
| Question cannot be answered | Ask about a named domain or supported structural finding. |

## Prototype boundaries

This is a local prototype with static analysis, OTel runtime analysis, authenticated workspaces and a read-only source security gateway (see `RUNTIME-USER-FLOW.md` and `PHASE-1-USER-FLOW.md`). Not built: production hardening, automatic source rewriting, billing and generated microservices (Source tasks produce reviewable patches only). Keep it bound to localhost. Validate runtime behavior and business context before acting on modernization recommendations.

A failed upload stays in the artifact folder until a retry succeeds or an operator deletes it. Successful processing deletes the uploaded artifact unless `RETAIN_ARTIFACTS=true`. Deleting failed uploads by age (a RETAIN_ARTIFACTS-style setting) is not implemented.


Security boundaries, runtime credentials, data flow, and deployment limitations are described in the [security whitepaper and FAQ](SECURITY-WHITEPAPER-FAQ.md).
