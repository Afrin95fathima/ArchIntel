## What the tool does

ArchIntel inspects a compiled Java application and produces architecture graphs, candidate domains, technical-debt findings, modernization readiness, and a suggested investigation sequence. The uploaded application is never launched. Results describe static structure, not proven production behavior.

Northstar Commerce is a **synthetic demonstration application**. Its results are generated by the same real jQAssistant â†’ Neo4j â†’ architecture-engine pipeline used for uploads.

## Start and stop

On the prepared Windows machine:

1. Open this project folder and double-click **Start-ArchIntel.cmd**.
2. Wait for â€œArchIntel ready.â€
3. The browser opens **http://127.0.0.1:8000**.
4. Complete administrator setup or sign in, then confirm **Services ready** in the top bar. See [Phase 1 user flow](PHASE-1-USER-FLOW.md) for the setup key and access controls.

Open **Local setup** in the left navigation for environment diagnostics. This page checks the configured database, local Java static-analysis runtime, and ArchIntel data folder. It distinguishes optional runtime-agent/local-model setup from container-based candidate build and security workflows, which are deferred in the local POC. Docker is not needed for ordinary static analysis or for receiving runtime telemetry; runtime capture also requires an OpenTelemetry Java agent in the application being observed.

The launcher starts workspace-local PostgreSQL and the API in hidden background processes. The prepared runtime does not require Docker or an external API key. Internet is needed for initial setup, not the prepared demonstration.

After a reboot, run the launcher again. To stop, wait for analyses to finish and double-click **Stop-ArchIntel.cmd**. Saved results remain in `.data/postgres`; do not delete that folder.

## Upload your own application

1. Select **Applications**, then **Analyze application**.
2. Choose a project or enter a new project name.
3. Enter an application name and version.
4. Choose a compiled `.jar` or `.war`, or a compiled project `.zip` containing one or more module `target/classes` / `build/classes` folders or module JAR/WAR files.
5. Click **Start architecture analysis**.
6. Follow progress until the overview appears.

Supported packaging: ordinary JARs, WAR classes under `WEB-INF/classes/`, Spring Boot classes under `BOOT-INF/classes/`, and compiled multi-module project ZIPs. A source-only ZIP is rejected: ArchIntel does not compile or execute uploaded application code. For Concord on Windows, package its existing build outputs with `powershell -NoProfile -ExecutionPolicy Bypass -File D:\vfunction\scripts\package-java-project-zip.ps1 -SourceRoot E:\concord\concord -OutputZip E:\concord\concord-compiled-classes.zip`. The ZIP is limited to compiled class files under recognized build-output folders and excludes VCS/dependency caches. A full source-repository checkout remains separately registered for source-task workflows.

Project ZIP classes from different modules are combined into one structural graph. Identical duplicates are collapsed. If modules contain different bytecode with the same fully qualified class name, ArchIntel analyzes the first normalized project path and records the selected and skipped paths in the ZIP manifest; the Overview calls out these conflicts. Review them before relying on dependencies involving those classes. Nested dependency JARs are not recursively scanned. Application references to external libraries are retained separately. Multi-release override classes are skipped; base classes are analyzed.

Default safety limits: 100 MB uploaded, 400 MB expanded, 50,000 entries, 20,000 classes, and 200,000 extracted dependency rows. These are protective limits, **not a measured large-application capacity guarantee**.

Unsafe paths, malformed archives, encrypted entries, symbolic links, duplicate normalized class paths, and excessive expansion are rejected. Upload artifacts are removed after successful processing by default. Failed inputs are retained for retry; structured results and the artifact hash are retained.

## Processing progress

The stages are validation, scanning, graph extraction/building, cycle analysis, metrics, domain discovery, issue analysis, modernization, and result persistence. Each stage records duration. A failed run reports the failed stage and never presents partial findings as completed results.

One job executes at a time. Up to four jobs can be queued/running. Refreshing the browser does not cancel a run. On startup, queued/interrupted work restarts from its original artifact when available; missing inputs produce an actionable recovery failure.

## Overview

The overview shows filtered application classes/packages, distinct internal dependency pairs, external references, candidate domains, issues, and average structural readiness. It also identifies the artifact SHA-256, scanner, and algorithm version.

A pair of classes can have several dependency types. Consequently, the typed-edge count may exceed the graph's distinct-pair count. Average readiness is not a forecast of migration cost, duration, or success.

## Architecture explorer

- Switch between **Domains**, **Packages**, and **Classes**.
- Click a node for details; double-click a domain/package to expand it.
- Use the domain filter to narrow a large view.
- Drag nodes, pan, scroll to zoom, and use the lower-right fit button.
- Clear the package filter to broaden a class view.

Arrows point **from the dependent to its dependency**. Views are capped at 150 displayed nodes and 2,000 edges; a notice identifies truncation. Edges require both endpoints to be visible. Class and package graphs remain separate: a package cycle can exist without a class cycle.

## Candidate domains

Cards show names, class/package counts, heuristic confidence, outgoing cross-domain ratio, issues, and readiness. Open a card for grouping evidence, database signals, dependency counts, and class membership.

Confidence is not a probability of business correctness. Validate boundaries and naming with domain owners. Current boundaries are automatically generated; manual editing is a future extension.

## Technical debt and cycles

Filter issues by severity, type, domain, or search text/package. Expand a finding to inspect its affected entity, evidence, significance, and recommended investigation.

Rules cover circular dependencies, large cyclic clusters, cross-domain coupling, god-class candidates, unstable-package dependencies, main-sequence deviation, high fan-in/out, and boundary violations. A god-class candidate requires multiple relative outlier signals, not method count alone.

Cycle cluster membership is complete; displayed cycle paths are bounded samples. Large clusters skip enumeration while retaining membership and internal edge counts. No short sampled cycle does not mean a strongly connected cluster is acyclic.

## Architecture metrics

| Metric | Meaning |
|---|---|
| Ca | Distinct outside classes that depend on a package's classes. |
| Ce | Distinct outside classes depended on by a package's classes. |
| I | Instability: `Ce / (Ca + Ce)`; zero when both are zero. |
| A | Abstract classes or interfaces / all package classes, counted once per type. |
| D | Distance: `abs(A + I - 1)`. |

Interpret instability with abstractness and architectural role. Neither high nor low instability is inherently good or bad. Isolated packages are identified separately. The scatter plot's diagonal is the main sequence; hover points for values.

## Modernization plan

Readiness is a 0â€“100 weighted structural score used to prioritize investigation. Higher scores reflect stronger cohesion, fewer cross-domain dependencies and cycles, and clearer data signals. Lower scores point to work such as cycle remediation, reducing boundary dependencies, or clarifying shared data access. It does not predict migration cost, duration, or success. Open a row or candidate-domain detail to inspect the assessment's actual components, weights, risks, and formula. Scoring has evolved; the formula stored with each assessment is authoritative.

Unknown database evidence receives a neutral component and remains an explicit risk. Its displayed range is sensitivity analysis, not statistical confidence. Evidence confidence describes support for the inferred boundary and is separate from readiness. The tool does not infer runtime SQL, transactions, table ownership, or a data migration plan.

The sequence is **dependency first**: prerequisites appear in earlier waves. Readiness prioritizes within a wave. Domains in the same cyclic group require coordinated remediation; their row order is not an independently executable extraction plan.

## Troubleshooting

| Symptom | Action |
|---|---|
| Cannot connect | Run the launcher and use port 8000, not an old development tab. |
| Services unavailable | Inspect `.data/api.err.log` and `.data/postgres.err.log`; retry the launcher after startup. |
| Scanner runtime incomplete | Follow setup/exporter-build instructions in the developer guide. |
| Upload rejected | Confirm a compiled JAR/WAR within the archive limits. |
| No internal classes remain | Have a developer review `EXTERNAL_PREFIXES` for your application's namespace. |
| Queue full | Wait for an existing run to finish. |
| Run interrupted by restart | Restart ArchIntel. Queued/interrupted runs resume automatically when their original artifact is available. If recovery reports a missing artifact, upload it again. |
| Scan failed | Correct the reported cause and start analysis again for the application. The failed input is retained for retry; the previous failed run remains in history. A checksum failure requires uploading the original artifact again. |
| Browser origin is not allowed | Open the tool directly at its localhost URL. A developer must explicitly configure trusted origins and hosts for a different deployment. |
| Question cannot be answered | Ask about a named domain or supported structural finding. |

## Prototype boundaries

This is a local prototype with static analysis, OTel runtime analysis, authenticated workspaces and a read-only source security gateway (see `RUNTIME-USER-FLOW.md` and `PHASE-1-USER-FLOW.md`). Production deployment hardening, automatic rewriting, billing and generated microservices remain future work. Keep it bound to localhost. Validate runtime behavior and business context before acting on modernization recommendations.

Failed scan artifacts are currently retained until a successful retry processes them or an operator removes them. Successful processing deletes the uploaded artifact unless `RETAIN_ARTIFACTS=true`. Automatic age-based failed-artifact retention is still planned.
